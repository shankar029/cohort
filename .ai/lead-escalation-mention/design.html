Design — Lead-first escalation, @mention wake, Frontend unblock

Repo: cohort · Branch: feat/lead-escalation-mention · Base: main · Research: research.md

1. Problem

When a specialist can't produce a deliverable, Cohort restarts its session once and then parks the run on a "NEEDS YOUR INPUT" prompt to the human (Retry/Skip). The Team Lead — an autonomous manager that already exists — is never asked to actually resolve the blocker. And the user cannot summon the Lead: a chat reply like "are you looking into this?" gets a conversational answer but does not make the Lead take over the parked task. The live "Snippet Vault" run shows the concrete failure: the Frontend Engineer hit an empty repo with no tech-stack decision and looped on self-directed clarifying questions, producing zero code, while Backend/UX made assumptions and shipped. Root cause detail: research.md §"Item 3".

2. Approach (three converging changes)

  1. Lead-first escalation (Items 1 & 3). Insert a Lead-resolve step before the human prompt in the no-code blocker path. The Lead makes the missing reversible decisions (tech stack, file layout, conventions), writes a concrete buildable spec into the task, posts it to the agent, and re-queues the task for one Lead-guided re-drive. Only if that also yields no code do we fall back to the existing user prompt (true last resort).
  2. @mention wake (Item 2). Parse an @lead / @team-lead / @<lead name> mention in chat(). On mention the Lead is "woken to act": beyond its normal reply, it takes over every pending blocker for the project — runs the Lead-resolve step and clears the parked Questions (answers them "Retry") so the human prompt disappears and the Lead drives. A lightweight "@ Team Lead" affordance is added to the chat input.
  3. Frontend rescue (Item 3). Falls out of #1: the Lead's decision supplies the tech stack + UI spec the FE was missing, so the re-drive has something concrete to build. No FE-specific special-casing needed.

3. Server changes — src/server/orchestrator.ts

  • State: private readonly leadAssisted = new Set<string>() (items the Lead already tried to unblock — one-shot) and private readonly noCodeQuestions = new Map<string,string>() (itemId→questionId, populated only where the no-code user prompt is raised) so the @mention take-over is scoped to no-code blockers ONLY (B1) and never touches build/integration/epic-review escalations.
  • New: private async leadResolveBlocker(agent, item, reason) (idempotent, one-shot decision):
    1. firstTime = !alreadyAssisted(item) where alreadyAssisted = leadAssisted.has(id) OR the item description already carries the decision marker (survives process restart — M2). Then leadAssisted.add(id).
    2. If firstTime: read the agent's latest notes (store.listNotes); ask the Lead actor to decide. Wrapped in try/catch — on failure fall back to a generic "ship the smallest working slice, decide minor things yourself" directive. Append the decision to item.description under a <!--lead-decision--> marker (store.updateWorkItem + publish workitem.updated), emit a system event, and postMessage it to main as the Lead addressed to the agent. If not firstTime: post a short "re-driving now" Lead message only (no duplicate decision — M1/N5).
    3. Resolve any tracked no-code question via resolveQuestionForItem(item.id): resolve the in-memory pending promise if present with a VALID choice ('Retry'), else mark the DB row answered directly (store.answerQuestion + publish) so it never stays stuck pending across a restart (M3); clear noCodeQuestions.
    4. Re-queue: awaitingInput.delete, setStatus(agent,'idle'), moveItem(item,'todo'), pokeLead().
  • No-code path (~2625): before setStatus('needs_input')+raiseQuestion, insert 
    if (!this.leadAssisted.has(item.id)) {
  await this.leadResolveBlocker(agent, item, 'no code after a session restart');
  return;
}
    The existing user prompt stays as the last resort (reached only when the item is already Lead-assisted). Because restartedForItem still holds the item, the re-drive gets exactly one more session attempt then escalates — bounded.
  • New: private async leadTakeOverPending(): iterate noCodeQuestions entries whose DB question is still pending; post ONE consolidated "taking over N blocked task(s)" Lead message (N5), then for each run leadResolveBlocker(agent, item, 'you asked the Team Lead to step in') (which resolves the question + re-drives). Scoped to no-code blockers only (B1). If paused, it still clears the question and annotates but posts that work is paused until resume (N3).
  • chat() (~586): compute mentionsLead = mentionsAgent(content, lead.displayName). Strip the mention token before intent classification (contentForIntent) so @lead alone does not trip buildIntent/discussIntent (N2). After the existing reply+route, if (mentionsLead) await this.leadTakeOverPending().

4. Web changes — src/web/pages/ChatPage.tsx

  • Add a small "@ Team Lead" button (data-testid="mention-lead") next to the composer that inserts @Team Lead into the input and focuses it. Purely a convenience to produce the token the server recognizes; the server is the source of truth. No new API surface.

5. Invariants & safety

  • The manager tick must never crash: every Lead ask is wrapped in try/catch; failures degrade to the generic directive and still re-queue.
  • Assistance is one-shot per item (leadAssisted) → no infinite Lead↔agent loop; the human prompt remains the guaranteed backstop.
  • No schema/domain changes; reuses Question, work_items.description, existing events. Response shapes and all other raiseQuestion sites are unchanged (Item-1 helper is adoptable by them later — research A4).
  • Fake-adapter friendly: the Lead's decision is plain text; in fake mode it returns canned text and the flow still re-queues deterministically, so it is testable offline.

6. Test plan

  • Unit: pure exported mentionsAgent(content, name) — matches @lead, @team-lead, @teamlead, @Team Lead (escaped displayName), leading or inline after whitespace; rejects negatives email@host, user@team-lead.io (requires a non-word char or start before @); RegExp-escaped name, no ReDoS (N4).
  • Integration (orchestrator, fake adapter):
    • A build task that produces no code triggers a Lead decision + re-queue (task back to todo, a Lead message posted, description annotated) before any pending user question is created.
    • After a Lead-assisted item still produces no code, the run falls back to the user prompt exactly once.
    • @team-lead chat on a project with a parked question clears the question (status→answered) and re-queues the blocked item.
  • E2E (Playwright, fake adapter): the "@ Team Lead" button inserts the token and sends; assert the parked "NEEDS YOUR INPUT" resolves (Lead takes over) — or, if timing is hard offline, assert the button wiring + a server integration test covers the behavior.
  • Full suite green via npx vitest run --no-file-parallelism; typecheck + lint clean.

7. Rollout / increments

  1. I1 — server: mentionsAgent helper + leadResolveBlocker + no-code path rewire + unit/integration tests.
  2. I2 — server: leadTakeOverPending + chat() mention wiring + tests; web "@ Team Lead" button + e2e.

  • M1: FIXED — leadResolveBlocker decides only on firstTime; otherwise a short re-drive message.
  • M2: FIXED — alreadyAssisted also reads the persisted <!--lead-decision--> marker.
  • M3: FIXED — resolveQuestionForItem marks the DB row answered directly when the resolver is gone.
  • N1–N5: pending-filter, strip-mention-before-intent, paused-note, escaped/bounded regex, consolidated notice — folded in.
  • N6: other raiseQuestion sites stay out of scope (A4); the map prevents the sweep reaching them.
