Design — Design-first orchestration for Cohort

Repo: cohort · Branch: feat/design-first-orchestration (stacked on PR #2) · Grounded in research.md · ≤3 pages

1. Problem & approach

Today decomposeEpic (orchestrator.ts:899) is dispatch-first, annotate-after: it fans out one generic task per stream via a deterministic template, then (step 5b, ~1148) asks the Architect for design notes — its prompt literally says "the team is already building." A scar-tissue NOTE (~925) warns that gating dispatch on a planning LLM turn once "stranded an epic with zero assigned tasks." Separately, the Frontend persona (catalog.ts:67) says "never introduce a new pattern when one already exists" — on an empty repo there is no pattern, so the FE loops on clarifying questions and writes nothing (the reported stall).

Approach (revised after design-review B1). Do not defer task creation. Keep the deterministic template board as a synchronous floor — makeTask creates the assigned per-stream tasks immediately, exactly as today, so the board is never stranded even on an instant crash (the scar-tissue invariant is preserved verbatim, not reinterpreted). What changes is when and how the Architect design informs those tasks: for non-trivial epics the structured design turn is moved to the front of decomposeEpic (today it runs as after-the-fact step-5b notes), and its per-stream acceptance criteria enrich the template tasks before builders act on them. Builders already awaitEpicDesign (orchestrator.ts:2624) and inject the design, so "design drives building" holds without any deferral. The template set is the floor for which streams exist (design may add detail, never under-dispatch below it — fixes M3). On timeout / error / architect-absent-and-lead-analysis-failed the tasks simply keep their template descriptions (AC3). Builder personas gain a QA-style decide-under-uncertainty clause. Agents resolve questions in bounded group discussions with a decider instead of blocking the user — generalizing the existing runGroupChat, writing the decision back under a distinct <!--group-decision--> marker (not the <!--lead-decision--> one — fixes M2).

4. Key interaction — non-trivial epic (design-first with fallback)

Lead.decomposeEpic(epic, content)
  worktree/branch                       (unchanged, best-effort)
  makeTask per kept stream  ───▶ TEMPLATE BOARD CREATED NOW (synchronous floor)   [never-strand]
  complexity = classifyComplexity(...)  (pure)
  if complexity == 'standard':
    designThenEnrich(epic, content, keptStreams, architectPresent):   [AC1,AC5]
      breakdown = await withTimeout(
          architectPresent ? architect.design(structured)
                           : lead.analyzeAndSplit(structured),
          ATEAM_DESIGN_TIMEOUT_MS)
      if breakdown ok ─▶ setEpicDesign; for each stream in (breakdown ∩ keptStreams):
                          append acceptance to that stream's EXISTING task     [AC1,AC5]
      else (timeout/error/empty) ─▶ no-op: tasks keep template descriptions     [AC3]
  # trivial ─▶ no design turn; template tasks stand as-is                        [AC2]
  verifiers + plan summary + PM criteria (unchanged); step-5b architect REMOVED  [M1]
  builders later awaitEpicDesign(2624) ─▶ act on the enriched, design-backed task

Agent-initiated discussion (AC6): a builder emits [[REQUEST_GROUPCHAT: topic]] → maybeHandleGroupChatRequest picks targeted participants → runGroupChat runs ≤N bounded rounds → the decider (Lead, or PM for a product question) posts a decision → decision written back onto the work item via the marker; no human question raised.

5. Data & contracts

  • No schema change. Reuse epic_designs (setEpicDesign/getEpicDesign) and the threads table unchanged.
  • Structured breakdown is parsed from the LLM turn as lines [stream] <title> :: <acceptance> (tolerant parser; unknown streams dropped; empty → fallback). No new persisted shape.
  • Decision write-back reuses the existing <!--lead-decision-->-style marker appended to workItem.description.
  • New env knobs (defaulted): ATEAM_DESIGN_TIMEOUT_MS (≈45000), ATEAM_DISCUSSION_ROUNDS (≈2). Documented; safe defaults.

7. Failure modes & edge cases

  • Design turn hangs / errors / asks a question → withTimeout + try/catch → template fallback. Board guaranteed.
  • Malformed breakdown (no parseable streams) → treated as empty → tasks keep template descriptions (no under-dispatch, M3).
  • Late design (withTimeout doesn't cancel the LLM turn, M4) → enrichment only rewrites a task still in todo/backlog; a design landing after a builder already started is still persisted for injection but does not rewrite an in-flight task — harmless.
  • Resume/restart mid-decompose → existingByStream idempotency + persisted epic_designs mean re-drive never duplicates; design is re-read, not re-generated.
  • Group discussion doesn't converge in N rounds → decider forces a decision; if the decider defers (ESCALATE:) → existing human backstop (raiseQuestion).
  • Runaway discussion nesting → existing groupDepth<2 guard retained + new round cap.
  • Trivial-classified but actually complex → builders still have the decide-under-uncertainty clause and can open a discussion; no dead-end.
