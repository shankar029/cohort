## Restatement
The plan replaces three ad-hoc gate blocks bolted to one transition inside `runWorkItemInner` with a single deterministic chokepoint `verifyWorkItem(item) → GateReport` that every path to `review`/`done` must pass. Reports (per-role required/advisory checks reusing the existing pure primitives — `producedRealChanges`, `runProjectBuild`, `checkClone`+`epicConstraints`, `runProjectTests`, integration result) are persisted, API-exposed, and asserted on by the harness instead of chat narration. A failing required check spawns a scoped fix work item to the same agent with a per-item fix budget, escalating to the user at the cap; integration into the epic clone becomes part of Definition of Done.

## Alignment with charter
- **Goal advancement:** Directly on-goal. The live defect (`prj_uNeRcw4CqhGl`: `done` while violating in-memory + epic tree empty) is a *decoupling* of "done" from "verified" and "integrated." A single chokepoint that all transitions funnel through is the correct structural fix — it converts an enforcement problem ("did we remember to gate this path?") into an invariant ("no report, no advance"). The report-as-audit-record and harness-asserts-on-reports changes are exactly what turns "we think it works" into "we can prove it did."
- **Non-goal drift:** One real drift risk. The per-role spec table hints at scope creep (docs `docs-present`, security `dep-audit`, coverage ≥80%). Coverage-as-required-check and narration-derived checks would *reintroduce* the non-determinism the plan exists to kill. Keep v1 to the four primitives that are already deterministic; defer anything measured from narration or unstable artifacts.

## Decision precedents
No `.pi/project/decisions.md` exists, so I treat the *in-code* precedents (FAITH-1 constraint gate, FAITH-3 scoping, I5 design-wait, I8 review budget) as the binding prior art. The plan is compatible with FAITH-1/FAITH-3 (it consolidates them, adds no new trust surface). The sharp conflict is with the **existing epic-level remediation machinery**: `epicReviewIter` (I8, `maxReviewIter`), `epicAcceptIter` (`MAX_ACCEPT_ITER=3`), `epicBuildIter` (`MAX_BUILD_ITER=3`), plus `createFixTask`/`createAcceptanceFix` already exist and already do "failed integrated check → tracked fix task → re-review, capped, then escalate." The plan proposes a *second, parallel* fix-and-budget system at the task level without reconciling it with the three epic budgets that are already live. That is the biggest structural gap.

## Top-3 risks
1. **Fix-task recursion resets the budget → unbounded livelock.** `createFixTask` (line 3560) mints a *new* `todo` work item under the epic. That new item runs through `runWorkItemInner` and can itself fail `verifyWorkItem` → spawn another fix task → ... If the per-item fix budget (`ATEAM_MAX_FIX_ITER`) is keyed on the work-item id, every spawned fix item starts at count 0, so the cap never bites — the epic livelocks generating fix tasks a human has to notice. Compounded by `maybeFinishEpic` requiring `children.every(review||done)`: a fresh `todo` fix child correctly re-holds the epic, so nothing forces convergence. This is the failure that would actually bite in a real run. Catch it early with a harness assertion capping total fix items per epic.
2. **`restartedOnce` is keyed by `agent.id`, not work item — cross-task escalation bug that the new budget will inherit.** Today `restartedOnce.add(agent.id)` (lines 2420/2498/2565/2640) means: once an agent restarts for *any* task, the *next* gate failure on a *different* task escalates immediately (no recovery round). The plan's "restart once then escalate for transient" and the new per-item fix budget will silently inherit this agent-scoping unless re-keyed to the work item. Blast radius: a busy specialist gets one shared recovery budget across all its tasks, so later tasks escalate to modal questions prematurely — exactly the "deadlock on a modal question" the plan set out to remove.
3. **Per-task-clone checks pass while the epic tree is empty/broken — the authority is in the wrong place.** The live defect was an *empty epic worktree*: the task clone had the `fs.writeFile` code (a per-task constraint check would have caught the constraint, had the guarded path run) but the integration never landed, so the merge authority never saw it. If `verifyWorkItem` runs required build/constraint checks against the **task clone** and treats those as sufficient for `done`, you re-create the same class of bug: green-in-isolation, absent-when-merged, or broken-only-after-merge. The integrated epic tree must be the authority for the merge decision, not the per-task clone.

## Alternatives worth a second look
- **In-place same-agent re-drive with injected evidence, over spawning a fix work item (the Q1 decision).** Re-driving the same agent on the *same* item with the deterministic violation list injected keeps one item, one per-item counter, and a natural audit trail (persist successive `GateReport`s as history on that item). Spawning a fix *item* per round adds board churn, a second clone, and the budget-reset recursion of Risk 1. Auditability — the stated reason to prefer fix items — is fully satisfied by persisting N reports against one item, *without* minting board items. This is the more loop-robust structure and I recommend it as the default path.
- **Collapse the epic remediation budgets instead of adding a fourth.** Rather than a new task-level budget alongside three epic-level ones, fold `epicBuildIter` + `epicAcceptIter` + new integrated-constraints/tests into ONE epic remediation budget with one "epic is remediating" latch. Fewer counters = far less livelock/double-count surface. The plan implicitly assumes the existing budgets stay as-is; they shouldn't.
- **Do NOT park the failed original in `review`.** The plan's parenthetical option ("move original to `review`, fix task carries the work") is a trap: `review` is a near-terminal state, and `maybeFinishEpic` treats `review` as ready. A failed item sitting in `review` with a fix child that then reaches `review` lets the epic finish with an unremediated failed report. Keep the failed item in `in_progress`/`todo` until its own report passes.

## Recommendation
PROCEED_WITH_CHANGES. The single-chokepoint + GateReport backbone is the right structure — it's the correct answer to "gates bolted to one path get bypassed by other paths," and the report model naturally de-duplicates a multi-failure delivery into one remediation round (a real strength: a delivery that fails build AND constraints is one report, one fix round, not two counters). But do not ship it with a second budget system layered on top of the three existing epic budgets, do not make the task clone the merge authority, and re-key recovery from agent to work item first. The changes below are prerequisites, not polish.

## Concrete changes I'd make to the plan (PROCEED_WITH_CHANGES)


**Q1 — fix-task vs in-place restart (recommend: in-place re-drive, item spawned only at handoff/escalation).** Default recoverable path = keep the item in `in_progress`/`todo`, re-drive the SAME agent with the failed `GateReport.checks` evidence injected into the prompt, persist a report each round, increment a per-item counter. Spawn a distinct tracked fix *work item* only when (a) reassigning to a different discipline, or (b) at the escalation cap for human visibility. Never park the failed original in `review`. This gives auditability (report history) without churn or the budget-reset recursion of Risk 1.

**Q2 — task clone vs integrated tree (recommend: BOTH, with explicit authority split).** Per-task checks run on the **task clone** as a fast, parallel-safe, owner-attributed PRE-FILTER (`produced`, `constraints` [pure], `build` [typecheck]). The AUTHORITATIVE required gate that blocks merge runs on the **integrated epic tree at epic-finish** (integrated `build` + `constraints` + `tests`), emitting an epic-level `GateReport` as the source of truth. `finalizeEpic` already runs integrated build + acceptance — extend it with integrated constraints + integrated tests and one epic report, rather than trusting per-task reports for the merge decision. This is the only structure that catches "passed in isolation, never landed, or broke on merge."

**Q3 — budget composition (recommend: one per-item + one unified per-epic + keep I8 separate).** (1) One PER-ITEM fix-round counter, keyed by work-item id, small cap (2–3), for task-clone pre-filter failures. (2) COLLAPSE `epicBuildIter`/`epicAcceptIter`/new integrated-constraints+tests into ONE `epicRemediationIter` + a single "epic remediating" latch, so parallel integrated-gate failures don't multiply fix tasks or double-count. (3) Keep the I8 `epicReviewIter` (human review comments) as a distinct class, but guard against epic-gate fixes and review-comment fixes spawning competing fix tasks for the same epic simultaneously — one remediation-in-flight latch per epic. (4) Increment budget PER FAILED REPORT, not per failed check (the report already aggregates). (5) Cap total fix items per epic as a backstop against Risk 1.

**Q4 — determinism traps in `runProjectBuild`/`runProjectTests`.** Introduce a distinct check status for infra failure: today `runResolved` maps timeout → `{ran:true, passed:false}` (indistinguishable from a real red build), and `ensureGateDeps` runs `npm ci`/`install` (network-dependent, 300s) on the hot path with install failure swallowed → the gate then fails spuriously for missing `tsc`/`vitest`. Map: `ran:false` → `skip` (n/a); genuine non-zero exit → `fail`; timeout or install/spawn error → `error`, which triggers ONE bounded retry and then counts as advisory, NOT as a budget-consuming required fail. Keep `build` = `typecheck` (pure, already preferred by `resolveBuildCommand`). Do NOT add coverage ≥80% as a required check unless read from a machine coverage artifact — narration-derived coverage is exactly the non-determinism to avoid. Persist `command` + exit + output tail as evidence so a flake is diagnosable and the report is reproducible-in-intent even though tests aren't pure.

**Q5 — migration + ordering.** "No report yet ⇒ must verify" is correct only where the chokepoint runs (new completions). For items ALREADY in `review`/`done` pre-migration, do NOT retroactively block on missing per-task reports — let the epic-level integrated gate (which reads the tree, not per-task history) be the authority; this sidesteps backfilling entirely. Ordering: keep per-task `verifyWorkItem` confined to the TASK clone + the integration-result boolean — do NOT run build/tests against the epic clone per-task, because that races `integrateSerially`'s merges into the same moving tree. Confine all epic-tree checks to epic-finish (already effectively serialized by the `epicReviewing` latch). Make `integrated` a genuinely required check: today a non-conflict integration failure (`!r.ok && !r.conflict`, ~line 2790) and a null `completion.hash` both fall through to `review` — the check must assert a real integration commit/record exists on the epic branch, else required-fail. Finally, `forcedAccept` (user "merge anyway") must write a recorded override report (`outcome:'skipped'`/override), never nothing and never `passed` — that is the one explicit recorded exception the plan allows.

**Also close the literal side-doors.** The Skip answers throughout `runWorkItemInner` and the conflict/needs-input handlers call `moveItem(item.id, 'done')` directly (e.g. lines ~2458, ~2517, ~2585, ~2660). These are the "side-door `moveItem(_, 'done')`" the plan's principle 1 forbids. Route every one of them through the chokepoint or record an explicit `outcome:'skipped'` report — otherwise the redesign leaves the exact bypass it set out to eliminate.

## Structural changes to make BEFORE coding
1. **Re-key recovery/fix budgets from `agent.id` to work-item id.** `restartedOnce` is agent-scoped today, causing cross-task premature escalation; the new per-item fix budget must not inherit this. Prerequisite for everything else.
2. **Fix the fix-task recursion.** If fix-on-failure spawns new work items, key the budget on the epic/lineage root and cap total fix items per epic — a per-item counter on a freshly-minted item resets to 0 and never converges. Prefer in-place re-drive (Q1) to avoid the whole class.
3. **Pick the authority explicitly: task clone = pre-filter, integrated epic tree = merge authority.** Wire the authoritative report into `finalizeEpic`, not only `runWorkItemInner`. Per-task reports attribute and pre-filter; they do not authorize `done`.
4. **Collapse the three epic remediation counters into one `epicRemediationIter` + a single remediation-in-flight latch,** before adding any new budget. Keep I8 review budget separate but mutually exclusive with gate-fix spawning.
5. **Make `integrated` a required check that asserts a real integration commit/record,** and close the fall-through where a non-conflict integration failure or null `completion.hash` still reaches `review`.
6. **Define four check statuses — `pass` / `fail` / `skip`(n/a) / `error`(timeout/install/infra)** — and only let genuine `fail` consume budget; `error` gets one bounded retry then advisory. Do this in the pure `verification.ts` module (Slice 1) so it's testable before wiring.
7. **Route all `moveItem(_, 'done')` side-doors (Skip/conflict/needs-input handlers) through the chokepoint or a recorded `skipped` report,** including the `forcedAccept` override path.
8. **Keep v1 checks to the four already-deterministic primitives.** Defer coverage%, `docs-present`, and `dep-audit` — none are deterministic today and each would reintroduce the narration-trust the redesign exists to remove.
